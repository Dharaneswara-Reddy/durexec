RE-RUN AFTER THE F9-2 WIRING FIX (image durexec-engine:phase6e)
========================================================================
The three blocks above were recorded against a binary in which the crash
seams were DEAD. cmd/engined never called eventlog.Store.UseFaultInjector and
never set runtime.Engine.Faults, so both injectors were nil and ShouldCrash
answered false silently. That was the real cause of F9-2 — not a missing
arming API. Both omissions are now fixed in cmd/engined/main.go.

---- 1. BeforeStartCommit (crash during workflow creation) ----
FIRED: yes, on the shard owner only (durexec-0=1 durexec-1=0).
attempt 1: HTTP 500; durable state executions=0 events=0 tasks=0
  -> the abandoned creation left NO TRACE, not merely "unchanged".
attempt 2: HTTP 201 Created (NOT 200/already_open)
  -> independent proof attempt 1 committed nothing: a half-created workflow
     would have made the retry a duplicate.
final: 8 events, 0 duplicate (run_id,seq) groups.

---- 2. AfterActivityJournaled (crash after result journaled, before ack) ----
workflow: f92-aaj2-1793086973
FIRED: yes, with the boundary named explicitly in the log:
  "injected crash after the activity result was journaled"
  shard=5 activity=ChargePayment seq=3
durable state: ActivityTaskScheduled=3 ActivityTaskCompleted=3
  -> exactly one completion per schedule. The worker abandoned the task AFTER
     the result was durable; on retry, replay found the journaled result and
     did NOT re-run ChargePayment. This is exactly-once-on-replay proven at
     the real boundary in the deployed binary, which was impossible before
     the wiring fix.

---- 3. BeforeDecisionCommit, MID-RUN (not on the start) ----
workflow: f92-midrun-1793087035
Method: started with prep_time_ns=150s so the run was in flight on a timer
with 3 activities already journaled, THEN armed and restarted. The crash
therefore landed on a decision commit for an EXISTING workflow rather than on
its creation, which is the case the start-path test cannot cover.
FIRED: yes (1 CrashInjected line).
final durable state:
  ActivityTaskScheduled=4  ActivityTaskCompleted=4
  TimerStarted=1 TimerFired=1 WorkflowExecutionCompleted=1
  status=COMPLETED   duplicate (run_id,seq) groups=0
  -> the abandoned decision was retried and the workflow completed exactly
     once, with no duplicated event and no duplicated activity.

LIMITATION, stated plainly: these seams return an error at the boundary; they
do not kill the process. They therefore test the DURABLE-STATE boundary and
not the loss of in-memory state or lease expiry. True process death is
covered separately by the Phase 9 SIGKILL work.
