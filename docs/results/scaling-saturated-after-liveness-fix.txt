Throughput scaling at 1, 2 and 4 shards, re-run AFTER the two liveness fixes.
Compare against docs/results/scaling-saturated.txt, which is NOT replaced.

Parameters matched to the published run. loadgen's measurement window is
(duration - warmup), so -duration 25s is what produces the published file's
20.000s windows:
  go run ./cmd/loadgen -mode scaling -sweep 1,2,4 -concurrency 64  -duration 25s
  go run ./cmd/loadgen -mode scaling -sweep 1,2,4 -concurrency 128 -duration 25s

concurrency 128 is run TWICE. A single 20s window at one shard count is one
sample, and the first attempt at this (scaling-after-liveness-fix-15s-window.txt)
produced a 2-shard figure well below the published one. Two samples is still
not many, but it is enough to say whether that was the engine or the run.

resume: either command above, on its own; each shard count is an independent
        window and the file is appended as each finishes.

Why this run was done at all: if workflow workers were dying during the
published load tests, the published throughput would have been UNDERSTATED,
because a shard with fewer workers processes less. This re-run is what decides
whether the published figures still stand.

Published figures this is being compared against:
  concurrency 64:   13.50 / 26.50 / 32.10 wf/s at 1 / 2 / 4 shards
  concurrency 128:  12.80 / 23.15 / 46.30 wf/s at 1 / 2 / 4 shards
                    1 -> 2 = 1.81x,  2 -> 4 = 2.00x
