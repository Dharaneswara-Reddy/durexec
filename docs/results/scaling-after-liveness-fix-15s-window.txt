Throughput scaling at 1, 2 and 4 shards after the two liveness fixes.
NOT COMPARABLE TO THE PUBLISHED RUN, and kept only as a second data point:
loadgen's measurement window is (duration - warmup), so -duration 20s gave a
15s window here, where the published file's windows are 20s. The matched
re-run is scaling-saturated-after-liveness-fix.txt.
Compare against docs/results/scaling-saturated.txt, which is NOT replaced.

Same commands and parameters as the published run:
  go run ./cmd/loadgen -mode scaling -sweep 1,2,4 -concurrency 64  -duration 20s
  go run ./cmd/loadgen -mode scaling -sweep 1,2,4 -concurrency 128 -duration 20s

resume: either command above, on its own; each shard count is an independent
        20s measurement window and the file is appended as each finishes.

Why this run was done at all: if workflow workers were dying during the
published load tests, the published throughput would have been UNDERSTATED,
because a shard with fewer workers (or none) processes less. This re-run is
what decides whether the published figures still stand.

Published figures this is being compared against:
  concurrency 64:   13.50 / 26.50 / 32.10 wf/s at 1 / 2 / 4 shards
  concurrency 128:  12.80 / 23.15 / 46.30 wf/s at 1 / 2 / 4 shards
                    1 -> 2 = 1.81x,  2 -> 4 = 2.00x
