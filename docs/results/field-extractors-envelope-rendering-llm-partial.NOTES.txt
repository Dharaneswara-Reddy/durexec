Why these 217 rows are in a file of their own
================================================================================

They are LLM-extractor rows from the envelope-rendering run
(field-extractors-envelope-rendering.csv), and they were measured AFTER that
run's report was written. Three facts explain why they are kept apart rather
than in either file:

 1. THEY POSTDATE THEIR OWN REPORT. field-extractors-envelope-rendering.txt
    describes 6,696 rows — the thirteen deterministic comparators over all
    three corpora. These 217 rows arrived later, from a process that was still
    running when the CSV was renamed. A results file whose contents and whose
    report disagree is worse than either, so the CSV was put back to exactly
    the 6,696 rows its report describes and these were moved here.

 2. THEY USE A RENDERING NOTHING ELSE USES. They embed the whole
    `Type({"args":"...","tool":"Type"})` envelope, which is the checker's
    generic fallback and NOT what the engine journals for the agent's tool
    calls. See the banner at the top of
    field-extractors-envelope-rendering.txt.

 3. THEY WERE MEASURED UNDER A BROKEN RATE. The run was paced at twenty-two
    extraction calls a minute against a provider limit of 8,000 TOKENS a
    minute and a measured cost of 634 tokens per call — about twelve calls a
    minute per key. Most calls came back 429, and an early version of the
    harness cached the empty reply, so some of these rows record a
    rate-limited call as "the extractor could not read this intent". That bug
    is described in field-extractors-llm-ratelimited-rows.NOTES.txt and is
    fixed: an unanswered call is no longer cached, it becomes an ERROR row,
    and ERROR rows are excluded from every figure and retried on a resume.

Nothing here is deleted and nothing here is a result. The LLM extractor's
measurements are in field-extractors.csv, rendered the way the engine renders,
and paced inside the token budget.
