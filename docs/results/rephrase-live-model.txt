HOW TO READ THE OUTCOME COLUMN

 Four outcomes, and two of them are neither a success nor a failure. They are the
 model doing something the scenario cannot use, and they are named rather than folded
 into a rate, because a rate computed over only the convenient trials is not a rate.

  usable       both incarnations invoked the domain's commit tool — the one with a side
               effect. There is a pair to compare, and these are the ONLY trials any
               catch rate below is computed over.
  never-acted  the pre-crash incarnation spent its whole step budget without invoking
               the commit tool, so there was no irreversible action for the crash to
               follow. Nothing was repeated and nothing was at risk.
  no-repeat    the recovered incarnation did not invoke the commit tool. It may have
               done nothing or only looked something up; after_tool_call_count in the
               CSV says which. On the control arm this is the CORRECT answer and is
               that arm's entire finding.
  failed       no pair was produced — unusable JSON from the model, or quota exhausted.

 And three classes WITHIN the usable trials, from ground truth read independently of
 every comparator (cmd/rephrase/truth.go, deliberately not the engine's extractor):

  identical    the model produced the same bytes twice. Exact matching catches these,
               and they are evidence AGAINST the project's premise, not for it.
  reworded     different bytes, same action. This is the case the project is about.
  drifted      one of the two sentences contradicts the goal on a deciding field. The
               model did not reword an action, it planned a DIFFERENT one. Reported
               separately and counted in NEITHER the catch rate nor the miss rate: on a
               drifted trial the second action is correct, and a comparator that
               suppressed it would have destroyed real work.

CONTROL ARM: WHAT A REAL MODEL DOES WHEN THE JOURNAL SURVIVED THE CRASH

 The main arm models a crash that lost its uncommitted events, so the recovered
 process re-plans the lost step from the same empty transcript. This arm changes one
 thing: the journal survives, so the recovered process replays the action and the
 model is asked for the NEXT step while looking at a transcript that already
 contains a CONFIRMED, irreversible result.

 control trials                                         15
 recovered run repeated the action                       0     0.0%
 recovered run issued no tool call at all               13    86.7%
 recovered run called only the read tool                 0     0.0%
 never-acted or failed before that question arose        2    13.3%

 This matters for how the fixture should be read. app/agent's scripted fixture
 re-issues the action in this configuration because its script says to. A real
 model, shown its own confirmed result, mostly does not — which means the rephrasing
 hazard does NOT arise from every crash. It arises from the crash that loses the
 planning step, which is the main arm, and that is a narrower claim than "an agent
 that crashes re-issues its action in new words".

WHAT IS MEASURED, WHAT IS ASSUMED, WHAT IS NOT MEASURED

 MEASURED
  - Every sentence compared here was produced by qwen/qwen3.8-27b over the network,
    at temperature 0.8, from a goal that suggested no phrasing. Both sides of the
    crash, in all five domains.
  - Every similarity score is a cosine between two 384-dimensional vectors from a
    running all-MiniLM-L6-v2 service. No cached vectors, no hash embedder.
  - Every verdict is produced by the engine's own comparator code at the shipped
    thresholds: exact.Key, semantic.Checker's pure path, and the same
    Checker.Compare call the hybrid path makes per candidate.
  - The side-effect counts are real invocations of each domain's commit tool,
    counted by the tool, not inferred from the verdicts.

 ASSUMED
  - That the fields each goal declares are the identity of the action. Everything
    the drift classification does follows from that, and it is a modelling choice
    rather than a measurement.
  - That the drift reader in cmd/rephrase/truth.go reads the model's sentences
    correctly. It is hand-written and it is deliberately NOT the engine's extractor,
    so the two can disagree; the raw sentences and the per-field readings are in the
    CSV so a reader can check every classification by eye. No person has done so
    exhaustively. In the message domain the subject is read with accept-only rules,
    so that domain cannot report drift on anything but the recipient.
  - That the simulator's crash is a faithful stand-in for a real one. It reproduces
    the one behaviour that matters — journaled work replays, lost work is redone —
    and it does so without a database or a network.

 NOT MEASURED, AND NOT TO BE INFERRED FROM THIS FILE
  - Any other model. One model, one temperature, one prompt shape. A rephrase rate
    is a property of the model and the prompt together, and this run varies neither.
  - THE PROMPT ASKS FOR VARIATION. The planner's system prompt contains the line
    "Vary your phrasing naturally between calls; do not repeat an earlier sentence
    word for word." It is the prompt the engine ships and runs, so measuring it is
    correct, but the rephrase rate above is the rate FOR THAT PROMPT. On the main
    arm the two planning calls each see an empty transcript, so there is no earlier
    sentence for the instruction to point at; it still cannot be assumed inert.
  - Precision and recall over a balanced corpus. This run has no negative class by
    construction: the drifted trials are whatever the model happened to get wrong,
    not a designed set of near-misses. docs/results/semantic-experiment-minilm.txt
    is where the precision/recall curve lives, on a corpus built for it.
  - The hybrid comparator on four of the five domains. The engine has one
    deciding-field extractor and it is flight-shaped. Where it cannot read an intent
    the hybrid column is the pure-semantic column. No extractors were written for
    the other domains, deliberately; see BY DOMAIN above.
  - End-to-end engine behaviour. The comparators are the engine's, but the workflow
    ran in app/agent's in-memory simulator, not against PostgreSQL on the cluster.
  - Whether a human reviewer would agree with any ESCALATE verdict. Nothing here
    asked a human anything.
