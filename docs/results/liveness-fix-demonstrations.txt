scaling re-runs because they prove something different: not "the published

pre-fix failures are recorded at the bottom of this file. A regression test

================================================================================
WHAT THESE RUNS DO NOT SHOW
================================================================================
Neither defect was observed firing on the live three-node cluster during the
re-runs in this directory, and that is expected rather than reassuring:

  - A sequence race needs two workers to reach the same seq for the same run at
    the same moment. The commonest way that happened was a lapsed ACTIVITY
    claim, which the second fix removes, so the first fix now mostly guards a
    narrower window (the gap between losing a lease and the lease manager
    noticing).
  - The heartbeat does nothing until an activity has been running for a third
    of TASK_LOCK, which with the shipped 30s lock is 10 seconds. Every activity
    in the demonstration applications finishes in under half a second.

So the live evidence here is that nothing REGRESSED. The evidence that the
defects are fixed is the tests above, which fail against the old code.

What to watch in a deployment, both new in this change:
    worker_task_failures_total{reason="seq_race"}       a lost race, worker continues
    worker_task_failures_total{reason="task_lock_lost"} an activity whose claim lapsed
and the log line "replacing exited shard workers", which in steady state should
never appear at all.
