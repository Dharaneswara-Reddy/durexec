Durable Execution Engine/ Architecture Reference/ Plates I & II

A system that cannot lose your work

This engine runs long, multi-step jobs — delivering a food order, running an AI assistant — and finishes them correctly even when computers crash halfway through. Every explanation here is written in plain language. Technical depth sits behind a marker in each panel, so it is available without ever being in the way.

§ 1

The whole idea, in one story

Imagine booking a holiday over the phone, and the call keeps dropping. Each time you ring back you explain everything again from the start — and you are never quite sure whether your card was already charged. That is what a crash does to ordinary software. This engine fixes it with four rules.

RULE 01

Write it down before you do it

Before taking any real action — charging a card, booking a flight, sending an email — the engine first writes down what it is about to do, in a permanent notebook.

RULE 02

Then do it, and write down what happened

The action runs, and the outcome goes into the same notebook on the next line. Two entries: the intention, then the result.

RULE 03

After a crash, read the notebook back

A fresh computer picks up the notebook and re-reads it from line one. Anything already written down is not done again — the recorded answer is simply reused.

RULE 04

Carry on where the notebook ends

The first step with nothing written beside it is the real work still outstanding. That is where it picks up, as though nothing had gone wrong.

That is the entire trick. A job's progress never lives in a computer's memory, where a crash would destroy it. It lives as lines in a database, where a crash cannot reach it. Everything else in this document is either machinery to keep that notebook accurate, or machinery to keep it safe.

§ 3

The vocabulary, in plain English

These terms appear throughout the project documents. Each names something simple — the intimidating part is usually just the name.

Workflowthe job itself
One complete multi-step job from beginning to end — everything involved in delivering one food order, say. It may take seconds, or days.
Activityone real action
A single step that touches the outside world: charge a card, send an email, book a seat. These are the steps that must never accidentally happen twice.
Event logevents
The notebook. An ordered list of everything that has happened to a job, only ever added to, never edited or erased.
Event sourcingthe overall approach
Treating that notebook as the only real truth. A job's status is not stored anywhere as a fact — it is worked out by reading the notebook.
Replayre-reading the notebook
Running a job's instructions again from the beginning, using the notebook to skip everything already done. This is how the engine recovers without redoing real work.
Deterministicpredictable
Given the same notebook, the job always makes the same choices. Without this, replay would take a different path after a crash and the engine would lose track of what it had done.
Idempotentsafe to repeat
An action you can do twice with the same result as doing it once. Pressing a lift button twice is idempotent. Charging a card twice is not.
Shardone filing cabinet
Jobs are split into 16 groups, so different computers can work on different groups at once without getting in each other's way.
Consistent hashingsharing that survives change
A method of deciding which computer looks after which cabinet, chosen because adding or removing a computer moves only a few cabinets instead of reshuffling everything.
Leasea badge that expires
Permission to be in charge of a cabinet, granted ten seconds at a time and renewed constantly. If a computer goes silent, its badge simply runs out.
Fencing tokena badge number that counts up
A number on the badge that increases every time it changes hands, letting the database reject writes from a computer that wrongly believes it is still in charge.
Sagaan undo plan
Unwinding a half-finished job by running the opposite of each completed step, in reverse order — refund the payment, release the reserved stock, and so on.
Transactionall or nothing
A group of database changes that either all happen together or none do. It removes the possibility of being caught halfway.
Embeddingmeaning as numbers
Turning a sentence into a list of numbers, so two sentences that mean the same thing produce two similar lists — even when the words are completely different.
