Executive Summary & Scope

1.1What the system does

A workflow is a business process made of several steps that must all happen — taking a payment, reserving stock, telling a restaurant, dispatching a driver. It can run for seconds or for days. This engine makes sure such a process finishes correctly even when the machine running it dies halfway through.

The mechanism is simple to state. Every decision a workflow makes is written to an append-only log in PostgreSQL before anything else happens. If the machine running that workflow disappears, another machine reads the log back, re-runs the workflow code against it, and arrives at exactly the point the old machine had reached. Steps that already finished return their recorded answer instead of running a second time.

Two properties make this more than a retry loop. First, work is split across a fixed number of shards, so adding a machine adds capacity. Second, ownership of each shard is decided by a renewable lease held in a database row rather than by an external coordination service such as ZooKeeper — which means the whole system has exactly one dependency.

The research contribution sits at one specific point in that flow. Before any real-world action fires, the engine asks whether it has already done this. Every existing engine answers that by comparing the request letter for letter. We also compare by meaning, which catches the case that matters for AI agents: an agent that crashes and re-plans re-issues the same intention in different words, and word-for-word matching lets it through.

1.2Scope

In scope

Event-sourced execution with deterministic replay; consistent-hash sharding; lease-based ownership with fencing; leader–follower replication; saga compensation; exact and semantic idempotency; two demonstration applications on one unmodified binary; a benchmark and fault-injection harness.

Out of scope

Hyperscale throughput; a full Raft implementation; multi-region deployment; cross-workflow transaction isolation; authentication and multi-tenancy beyond a shared secret; a visual workflow builder; garbage collection of old event history.

System Architecture

2.1Pattern, and why not the alternatives

The system is a replicated, sharded monolith: one Go binary, deployed three times, with all coordination pushed into PostgreSQL. That choice is deliberate and worth defending because the obvious alternatives are worse here.

Rejected — microservices

Splitting the gateway, scheduler, workers and lease manager into separate services would add network hops inside the hot path and a service mesh to operate, while solving no problem this system has. The components share one database and one failure domain by design.

Rejected — serverless

Functions cannot hold a workflow coroutine across a multi-day sleep, and per-invocation billing punishes exactly the long-lived, mostly-idle workloads this engine targets.

Rejected — external coordinator

ZooKeeper or etcd would give correct leader election, and a second distributed system to install, monitor and reason about. PostgreSQL already provides linearizable compare-and-swap, which is all shard ownership needs.

Chosen — database-centric

The log, the queue, the timers, the ownership record and the meaning-vectors live in one transaction domain. That is what lets a workflow's entire decision commit atomically, which is the property the whole design rests on.

2.2Topology

A node is one operating-system process containing a handful of goroutines: an HTTP server, one lease manager, and per owned shard a timer scanner, four workflow workers and eight activity workers. Each worker is a plain loop — poll, work, commit, repeat — that backs off from 10 ms to 1 s when the queue is empty, so an idle cluster does not hammer the database.

There is no leader among the nodes and no membership protocol between them. A node discovers what it owns by reading shard_leases, and discovers it has lost something when a transaction refuses to commit.

2.3Sharding and ownership

The gateway is stateless and is allowed to be wrong. If a request lands on a node that no longer owns the shard, that node answers 409 NotOwner with the current owner. Correctness is enforced at the write, never at the route — which is precisely why routing needs no consensus.

As built — the retry half now lands, server-side The paragraph above used to be only half true: every node correctly refused work for a shard it did not own, but nothing performed the retry on the client's behalf, so a client that was not shard-aware hit the wrong door on roughly two requests in three. That gap is now closed. A node that receives a request for a shard it does not own now forwards it to the node that does, and relays the answer back, so the caller never sees the miss. Two independent bounds stop the obvious failure mode of a forwarding layer — a routing loop between two nodes that disagree about who owns what: an X-Durexec-Forwarded-By header means a request that has already been forwarded once is served or refused locally, never forwarded again, and a hard cap of two outbound attempts per inbound request (internal/api/forward.go) means a confused cluster gives up quickly rather than being walked node to node. If the named owner cannot be reached at all, the node answers 503 naming that owner rather than hanging or guessing — a response that is safe to retry because nothing was attempted against it. Verified live: a POST to node-a for a shard owned by another node returned 201 Created, the caller never seeing the miss. Correctness is unaffected either way — the owner still re-verifies its fencing token inside the commit transaction, exactly as before forwarding existed.
As built — the ring existed but decided nothing A consistent hash ring that nobody consults is decoration. lease.ManagerConfig always had a Wants hook built for exactly this purpose — the ring narrows which shards a node reaches for — but cmd/engined never set it. Every node therefore wanted every shard, and whichever node finished booting first won all sixteen leases before its peers got a chance to try. Verified live before the fix: node-b owned all 16 shards, node-a and node-c owned 0.

Wants is now wired to ring.Lookup: a node only reaches for a shard the ring assigns it, which is what actually produces an even split. That alone is not sufficient for failover, though — a preference with nothing backing it up means that if a preferred owner dies, the ring still says its shards belong to a node that is not coming back, and nobody else will try for them. So a node also adopts an orphan: a shard whose lease has sat expired for more than twice the lease TTL. The wait is deliberate — it stops a brief GC pause or a rolling restart from causing needless shard churn between nodes that are all still alive. Verified live after the fix, three nodes: 4 / 9 / 3 shards.

The ring's membership list is a new required setting, CLUSTER_NODES — a comma-separated list of every node id in the cluster, added to the configuration surface in §4.3. Every node needs the identical list, because the ring is a pure function of it and two nodes computing it from different membership would silently disagree about who owns what.
As built — one database, not sixteen The figures on this page (Fig 1, Fig 5, Fig 7) show a database per shard, and that was the original intent: an independent PostgreSQL instance per shard would give each shard's log its own failure domain, so one shard's database trouble cannot touch another's. What was actually built, and what deploy/docker-compose.yml actually starts, is one PostgreSQL leader and one streaming-replication standby, shared by all sixteen shards and all three nodes. Every table added shard_id as the leading column of its primary key from the first migration (migrations/0001_init.up.sql) specifically so this would still be safe: two shards never collide on a row, because no primary key is complete without naming which shard it belongs to.

This is honestly a weaker version of the independent-log argument in §2.1. Sixteen shards sharing one Postgres share its connection limit, its buffer cache, its WAL, and — most importantly — its availability: a leader that is down for maintenance or recovering from a crash takes every shard down with it, not just one, which is a materially worse failure blast radius than the design originally claimed. The single-writer-per-shard argument in Fig 2 above still holds — nothing about sharing a database lets two workers write the same (shard_id, workflow_id, run_id, seq) — but the fault isolation argument does not, and the report should say so plainly rather than let it be discovered.

What it would take to change: because every key already carries shard_id, moving to one database per shard (or one per a group of shards) is a deployment change, not a schema change. It would mean routing each shard's connection pool at a different DATABASE_URL, running migrations/ against each target, and teaching the lease manager and the ring which database backs which shard — none of which requires touching a single table definition. That is deliberate: the schema was built to make this move possible later without a rewrite, even though the demonstration cluster does not exercise it. It remains a stated extension, not a current property.

2.4Failure model and the fencing argument

We assume nodes crash without warning, pause arbitrarily long, and come back believing no time has passed. We assume the network drops and reorders messages. We assume PostgreSQL is a single linearizable source of truth and that its own failover is handled by streaming replication. We do not assume clocks are synchronised.

The invariant A node that has lost ownership of a shard cannot mutate that shard's state, regardless of what it believes about the world. This is Kleppmann's fencing-token argument implemented in a table rather than in ZooKeeper, and it is the same technique Temporal uses under the name RangeID.
Stated honestly This is not consensus. The coordination problem has been moved into PostgreSQL, not eliminated. The system inherits the database's availability, and a shard is unavailable for up to the lease TTL between an owner dying and a successor acquiring. Both are measured and reported rather than glossed over.

3.2The workflow task loop

This is the mechanism the entire system is built around. A workflow task means: this workflow has new history — run its code forward until it blocks again.

The join between "the call the code is making right now" and "the event that recorded that call last time" is k, a counter incremented once per blocking call in program order. It is never stored in the source. It is recomputed identically on every replay because the code takes the same branches, because the code only ever reads from history.

If the code takes a different branch on replay, k shifts and the match fails. The engine cannot repair this — it has no way to know which version of the code told the truth — so it refuses to continue and raises a non-determinism error naming the sequence number, the recorded activity type and the requested one.

The queue poll — SKIP LOCKED is not optional

UPDATE tasks
SET locked_until = now() + interval '30 seconds',
    lock_token   = gen_random_uuid(),
    attempt      = attempt + 1
WHERE (shard_id, task_id) IN (
    SELECT shard_id, task_id FROM tasks
    WHERE shard_id = $1 AND task_type = $2
      AND visible_at <= now()
      AND (locked_until IS NULL OR locked_until < now())
    ORDER BY task_id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
RETURNING *;

Without SKIP LOCKED every worker serialises behind a single row lock, and the queue stops scaling at one consumer. It is the difference between a design that uses N workers and one that merely deploys them.

3.4Semantic idempotency

The contribution, and the part of the design most likely to be challenged. The interesting decision is not the similarity metric — it is where the check runs.

Why it cannot live in the activity worker A similarity check is non-deterministic: it depends on a model, a float threshold and a candidate set. Placed inside the activity worker it would either be recomputed on replay — possibly differently, diverging the history — or skipped entirely, making the workflow's decision irreproducible. Either outcome destroys the replay invariant the whole engine rests on.

So the verdict is computed once, on the workflow path, and journaled as a SemanticDedupEvaluated event. It is the existing SideEffect mechanism applied to a deduplication decision. Replay reads the recorded verdict and performs no network call at all.

Decided — D5, the ESCALATE band executes by default This was left open at design time (§7, D5) and has since been resolved, in the direction opposite the original proposal. By default, the ESCALATE band runs the activity, exactly as DISTINCT does, and journals the verdict alongside it so the uncertainty is fully visible in the audit trail. Setting ESCALATION_BLOCKS=true switches to the originally-proposed stricter policy: the activity is not scheduled, and the run parks on an unresolved future until a person answers the durable __adjudicate signal.

The reasoning follows directly from the project's own risk table (§3.4, below): the two ways of being wrong in this band are not equally bad. A false positive — calling something a duplicate when it was not — makes the engine silently drop a real action, with nothing erroring anywhere to notice it by. That is the severe, asymmetric failure this whole mechanism exists to be honest about. A false negative — running something that actually was a repeat — is no worse than the engine's behaviour with no semantic check at all, because the exact-match dedup key still travels with the call and the downstream service still gets its chance to catch the repeat. Running the activity by default in the uncertain band therefore guarantees the mechanism can never be worse than the exact-match baseline on the dangerous axis; it can only ever be better, on the other. Nothing about this hides the uncertainty — the verdict, its similarity score and both thresholds are journaled in the same transaction either way, so the width of the band and what fell into it remain fully measurable. Both policies exist behind one flag specifically so the evaluation can run the identical workload both ways and report the comparison, rather than asserting one is right.

Two consequences are worth stating explicitly. Recovery never depends on the embedding service being reachable, because replay never calls it — a design that re-embedded on every replay would have coupled crash recovery to a third-party API. And every skipped action is explainable from a row: score, threshold, matched call index, model identifier. For a mechanism whose job is to not perform real-world actions, that audit trail is what makes it deployable at all.

FailureMeaningCostMitigation
False positiveTwo genuinely different calls judged duplicate; a real action is silently skipped.Severe and asymmetric — a flight the user wanted is never booked, and nothing errors.Opt-in per activity; conservative τ; escalation band; every verdict journaled and surfaced.

That asymmetry is the honest core of the contribution and is presented as a designed-for constraint rather than left to be discovered: the mechanism is strictly better than baseline on false negatives and strictly worse on false positives, which is exactly why it is opt-in, thresholded conservatively, and fully audited.

4.2Continuous integration

Why the fault stage is in CI, not in a notebook The central claim of this project is a safety property. A property that is only checked by hand before a demonstration is a hope; a property checked on every merge is a guarantee. The stage runs the cluster, kills the owner of shard 2 mid-load, and fails the build if the event log contains a single duplicated sequence number.

4.3Configuration surface

SettingDefaultEffect of changing it

4.5Memory budget

NFR-9 sets the operational footprint at under 3 GB on one machine. The base stack — three engine nodes, the PostgreSQL leader and standby, Prometheus and Grafana — measures at 2300 MB, comfortably inside the 3072 MB (3 GB) target.

The real embedding service is an opt-in overlay, on purpose A real sentence-embedding model needs headroom the base stack does not budget for — CPU sentence-transformers plus a CPU build of torch want roughly 900 MB on their own, which would put the whole stack at 3200 MB and break the NFR-9 claim outright. Rather than quietly exceed the target, that service lives in a separate overlay file, deploy/docker-compose.embedder.yml, started only with make up-semantic. The default path, make up, never pulls it in.

Without the overlay, the engine falls back to a built-in deterministic stand-in encoder: it hashes the intent text into a vector, so an exact repeat still scores a perfect match and is still caught, but it has no notion of meaning — a reworded repeat hashes to an unrelated vector and is not recognised as one. That is enough to exercise every piece of plumbing (the journal, the replay path, the audit trail) end to end on a laptop with nothing else running, but only the real encoder — under make up-semantic, at 3200 MB, deliberately over budget for the duration of that measurement only — demonstrates the actual contribution.

Implementation Findings

A document that only records what was intended is a proposal. A document that also records what went wrong, how it was found, and what it cost, is evidence the system was actually built and actually tested. The five defects below (§6.1–§6.5) surfaced through measurement, not code review, and each one changed a real number in the evaluation before it changed a line of prose here. §6.6 presents the evidence that the assembled system meets its central claim, and §6.7 records a limitation that survives into this revision honestly rather than being fixed under deadline pressure.

6.1The hash ring's clustering defect

§2.3's central sharding claim is that adding a node moves a minority of shards — an ownership handoff, not a data migration. The ring that was supposed to provide that property did not, and the reason is a specific, checkable mixing defect rather than a vague "the hashing was off."

What was wrong The ring placed nodes and looked up keys with raw FNV-1a. FNV-1a mixes upward only: each byte is folded into the low bits and the accumulator is then multiplied, so by the time hashing reaches the end of a short string, the high bits — the ones that decide ring position — have been shaped almost entirely by the string's length and its first few characters. The sixteen shard keys "shard-0"…"shard-15" are exactly such a set: the ten seven-character names collapsed onto one point around 0x8ae4…, and the six eight-character names onto another around 0x6749…, each cluster spanning about 1e10 inside a 64-bit space of 1.8e19. For a clockwise-walk ring, a cluster that tight is indistinguishable from a single point. At most two nodes could ever own a shard, at any cluster size, and adding a fourth node to a three-node cluster moved zero of sixteen shards — the exact opposite of the property a consistent hash ring exists to provide.

The fix. hashRing now runs its FNV-1a output through splitmix64's finalising avalanche step — three xor-shift/multiply rounds that spread a one-bit input difference across all 64 output bits — before the value is used for ring placement. The cost is a handful of nanoseconds per ring point, paid once when the ring is built.

Each transition lands within a tight band of its ideal fair share (1/n), which is the actual, checkable version of "adding a node moves about one node's worth of keys."

6.2The task queue's silent starvation under concurrency

The SKIP LOCKED poll in §3.3 is correct in isolation and wrong under load, in a way that a single-worker test cannot see and a lightly-loaded demo will not trigger.

What was wrong The original poll was the textbook spelling: UPDATE tasks SET … WHERE (shard_id, task_id) IN (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1). Under PostgreSQL's default READ COMMITTED isolation, when that outer UPDATE reaches a row that a concurrent transaction has just modified, PostgreSQL re-evaluates the uncorrelated subquery during EvalPlanQual to decide whether the update should still apply. The re-run of the subquery now sees the winning transactions' locks already held, SKIP LOCKED steps over every one of them, the recheck finds nothing to update, and the poll reports "no task available" — while the tasks are sitting there, unclaimed, the entire time. It hid during development because cold database connections stagger pollers by roughly 17ms, long enough for each to finish before the next begins; it only appears once several warm connections poll at genuinely the same instant.

Measured, before and after (internal/taskq/concurrency_test.go)

SetupBefore the fixAfter the fix
4 warm pollers against 4 available tasks, 12 rounds1 poller got work, 3 got nothing — in 12 of 12 rounds48 of 48 polls succeeded across 12 rounds

The fix. The same lock-and-pick logic is rewritten as a single-pass CTE — WITH pick AS (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) UPDATE tasks … FROM pick … — so the row selection, the lock and the skip all happen once, inside the same plan, instead of being re-derived after the fact.

Correctness was never at risk No task was ever double-claimed and no event was ever lost — a poller that lost the race simply tried again on its next tick, and the queue's lease-with-expiry design (§3.3) absorbed the retry for free. What the defect cost was throughput: with three of four workers idling every round under load, the queue could not come close to using the worker pool it was configured with. That is precisely the axis NFR-5 (throughput scaling) measures, so this defect would have understated the engine's own headline number without ever showing up as an incorrect result. It is exactly the kind of finding that is more convincing in a viva than a feature would have been, because it shows the difference between code that passed its tests and a system that was measured under the conditions it claims to handle.

6.3A migration race on first boot

Three engine nodes booting together all run the same schema migrations on startup (§2.5, §4.2), and that concurrency was never actually exercised until the demonstration cluster came up with all three nodes cold at once.

What was wrong CREATE EXTENSION IF NOT EXISTS vector — the first statement in migrations/0001_init.up.sql — is not atomic against a concurrent creator. Its existence check and its insert into pg_extension are two separate steps, so when two nodes reach it in the same instant, both see "not there," both attempt the insert, and the loser dies with a unique violation on pg_extension_name_index. CREATE TABLE IF NOT EXISTS can fail the identical way. Neither is a bug in PostgreSQL; it is what "IF NOT EXISTS" always meant — not present at the moment I checked — applied somewhere that check-then-act is not safe without help.

The fix. eventlog.Migrate now takes a PostgreSQL session advisory lock (pg_advisory_lock) on a fixed key before applying any migration file, and releases it when done. The first node to arrive migrates while its peers block on the same lock; each of them then finds the schema already in place and its own IF NOT EXISTS statements become genuine no-ops rather than a race. This is not defensive programming added out of caution — without it, a three-node cluster reliably fails to start on a cold volume, because all three nodes migrate on every boot by design (§2.5: there is deliberately no migrations-applied bookkeeping table to keep in sync across nodes).

6.4Connection pool sizing

This one was found by the database refusing to talk to the cluster at all, not by a subtle timing window — the loudest possible failure, from the quietest possible cause: a sum that was wrong by 3×.

What was wrong Each node's connection pool was sized ShardCount × (WorkflowWorkers + ActivityWorkers) + 8 — one connection reserved per worker goroutine, per shard the node could ever own, plus a small margin. At the running defaults that is 16 × (4 + 8) + 8 = 200 connections per node, or 600 across the three-node demonstration cluster, against PostgreSQL's default max_connections of 100. The server did exactly what a correctly configured server should do under that load: once the limit was reached it started refusing new connections outright, with "sorry, too many clients already".

The fix. The sum was wrong at the premise, not the arithmetic: a worker holds a database connection only for the duration of one query, not for its whole lifetime, so the pool never needed a permanent slot per worker in the first place. Between polls a worker holds nothing. The pool is now capped at a flat 25 connections per node — comfortably inside a default server across three nodes, with room left for psql and the monitoring stack — and a burst of workers that briefly exceeds it simply queues for a free connection rather than deadlocking, which is exactly the back-pressure wanted when the database, not the worker pool, is the bottleneck.

6.5The standby that was never replicating

FR-9 claims a real, verified follower. For a stretch of development the standby container reported unhealthy and never recovered, and the reason was a single missing word in a shell script — the kind of defect that is invisible until something forces the question "is it actually replicating, or just running?"

What was wrong deploy/postgres/standby-entrypoint.sh cloned the leader with PGPASSWORD="$REPL_PASSWORD" pg_isready … to wait for the leader to be ready, then later ran pg_basebackup to perform the actual clone. A prefix assignment like VAR=val cmd sets that variable only for the one command it prefixes — it does not persist in the shell's environment afterwards. So pg_basebackup, running moments later with no PGPASSWORD in scope at all, was rejected by the leader's scram-sha-256 authentication with "fe_sendauth: no password supplied". The script had set -e, so that failure killed it immediately, and the container's restart policy brought it straight back into the same failure — postgres itself never finished starting, which is why the healthcheck never turned green: there was nothing behind it to check.

The fix. Changing the one line to export PGPASSWORD="$REPL_PASSWORD" before the clone keeps the password in the environment for every command that follows, including pg_basebackup. deploy/check_replication.sh makes the fix demonstrable rather than asserted: it writes a one-off sentinel row on the leader and polls the standby until that exact row shows up there, which is the only way to actually prove WAL is being applied rather than merely that the container reports itself healthy.

6.6The failover demonstration: results

§2.4 argues that the fencing mechanism makes a stale node unable to corrupt a shard it has lost, and P3/P8 in §5 set an exit condition for that argument: kill the owner mid-workflow and show that nothing is lost and nothing is duplicated. The other findings in this section were defects in the machinery underneath that claim. This one is the claim itself, run for real, with the numbers it produced.

What was run, on the live three-node cluster A workflow was started on the shard owned by node-b, with a 25-second durable sleep in its history. node-b was killed mid-flight with docker kill. Shard 3 — the shard that workflow lived on — moved to node-c, and its fencing token incremented from 1 to 2, exactly as §2.4's argument requires. The workflow nonetheless reached COMPLETED, at last_seq=12, with exactly four ActivityTaskCompleted events and none of them duplicated. The durable timer survived the failover intact: TimerStarted at seq 8 and TimerFired at seq 9, on either side of the kill, with no re-firing and no lost wakeup.

Database-wide assertions after the run (deploy/assert_no_duplicates.sql, cmd/acceptance/analyze.go)

Duplicated (shard_id, workflow_id, run_id, seq) tuples in events0

This is the P3/P8 exit condition from §5, met on the running system rather than asserted about it: a workflow's owner dies mid-execution, ownership and the fencing token both move, and the workflow still finishes exactly once — no event replayed twice, no activity re-run, no timer either lost or re-fired. Combined with the CI fault-injection stage in §4.2, this is checked on every merge, not only when someone remembers to run it by hand.

6.7Known limitation: the cluster does not rebalance on recovery

The demonstration above shows the failure side of fault tolerance working. The recovery side has a real gap, and it is worth stating plainly rather than leaving it to be noticed.

What happens today When a node that died is brought back up, it does not get its shards back. In the run above, restarting node-b left it owning zero shards: node-a and node-c had already adopted everything it used to hold, and both keep renewing those leases on schedule, so nothing about them ever looks expired. §2.3's orphan rule only lets a node take over a lease that has sat expired for more than twice the TTL — deliberately, so a brief GC pause does not cause needless churn — but a live, renewing lease never qualifies as an orphan no matter how long ago the ring's preference changed. Repeat this enough times across enough failovers and ownership keeps concentrating onto whichever nodes happen to survive, until one node is carrying shards the ring says several other nodes should hold.

Fixing this needs a mechanism the engine does not yet have: a handback. A node that is currently holding a shard the ring assigns to a live peer would need to notice the mismatch and voluntarily release the lease, rather than simply continuing to renew whatever it already holds. Nothing in the current design triggers that check — Wants (§2.3) only ever governs which shards a node reaches for, never which ones it gives back. This is recorded as accepted, known future work rather than as a defect fixed in this revision, because it does not threaten correctness — a lopsided cluster still answers every request correctly, just from fewer nodes than it should be using.
