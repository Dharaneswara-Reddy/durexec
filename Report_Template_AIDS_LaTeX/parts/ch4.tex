\chapter{System Design}

This chapter describes the design of the engine in two parts. The high-level
design (Section~\ref{sec:hld}) presents the architecture, the separation of
workflow and activity code, the mapping of workflows to shards and nodes, and
the ownership protocol. The low-level design (Section~\ref{sec:lld}) gives the
data model, the workflow task loop, the crash-window analysis, sagas and the
semantic deduplication path.

\section{High-Level Design}
\label{sec:hld}

\subsection{Governing principle}

One rule governs the design: \emph{the event history is the only state of a
workflow run, and every decision is committed to it before it is acted on}.
A node holds caches, worker goroutines and open connections, but nothing that
would be lost if the process were killed. Recovery therefore never needs to
reconstruct a node's memory; it needs only to replay a run's history, on any
node that currently owns the run's shard.

\subsection{Architecture}

Fig.~\ref{fig:arch} shows the components. Clients reach any engine node
through an HTTP API to start runs, send signals and read status. Each node is
one Go process with four parts: the API server, a lease manager that acquires
and renews shard leases, a pool of workflow workers that execute workflow
code, and a pool of activity workers that execute side effects. All nodes run
the same binary; any of them can own any shard. PostgreSQL holds the event
log, the task queue, timers, leases and intent embeddings. There is no other
shared component.

\subsection{Separation of workflow and activity}

Workflow code and activity code have opposite requirements, and the engine
treats them differently. Workflow code decides what to do next. It is
re-executed on every recovery, so it must be deterministic and must perform
no input or output; it calls \cd{ExecuteActivity}, \cd{Sleep},
\cd{WaitForSignal} and \cd{SideEffect} on a context object, each of which either
returns a result recorded in the history or suspends the workflow until one
is available. Activity code performs the side effects. It may be
non-deterministic, may fail and may take a long time; it runs at least once
and its result is recorded when it completes.

A workflow function in the engine's Go SDK has the following shape.

\begin{lstlisting}[caption={A workflow with two activities and a saga
  compensation}, label={lst:workflow}]
func Order(ctx workflow.Context, in OrderInput) (Receipt, error) {
    s := saga.New(in.OrderID, runner(ctx))
    var pay Payment
    if err := ctx.ExecuteActivity("charge_card", in.Card).Get(&pay); err != nil {
        return Receipt{}, err
    }
    s.AddCompensation("refund_card", pay.ID)   // only after success
    var res Reservation
    if err := ctx.ExecuteActivity("reserve_stock", in.Items).Get(&res); err != nil {
        return Receipt{}, s.Compensate()        // runs refund_card
    }
    return Receipt{Payment: pay.ID, Reservation: res.ID}, nil
}
\end{lstlisting}

\subsection{Two-level mapping of workflows to nodes}

A workflow identifier is hashed to one of $S$ shards, with $S=16$ by default,
and the shard never changes for the life of the run. Shards are assigned to
nodes by a consistent-hash ring with 150 virtual nodes per engine node
(Fig.~\ref{fig:mapping}). The ring expresses a preference only: a node
reaches for the shards the ring assigns to it, and holding a shard is decided
by its lease. Because all data lives in the shared database, moving a shard
between nodes moves no data; the new owner simply begins to poll that shard's
task rows.

Two rules make the preference converge after failures. A node may adopt a
shard that the ring does not assign to it if the shard's lease has been
expired for more than twice the lease period, which is taken as evidence that
the owner is not coming back. A node that holds a shard the ring assigns to
another node returns it as soon as that node answers its health check. The
first rule prevents a dead node's shards from stalling forever; the second
keeps the load even after the node recovers. The delay in the first rule
avoids needless handovers after a short pause or a rolling restart, and its
cost appears in the freeze results of Chapter~7.

\subsection{Leases and the fencing invariant}

Each shard has one row in \cd{shard\_leases} holding the owner, an expiry time
and a fencing token. A node acquires a free or expired lease with a single
conditional update that increments the token and sets the expiry to the
database's \cd{now()} plus the lease period of 10\,s. It renews every 3\,s,
so a node has three attempts before its lease lapses. Expiry is computed on
the database clock, so clock skew between engine nodes does not matter.

A lease alone is not safe. A node that is paused for longer than the lease
period resumes believing it still owns its shards, while another node has
already taken them over. The engine therefore enforces the following
invariant at the point of writing:

\begin{quote}
\emph{Every transaction that changes the state of a shard first reads that
shard's fencing token with} \cd{SELECT ... FOR UPDATE}\emph{, and commits only
if the token equals the one the writer was granted.}
\end{quote}

The row lock is held until the transaction ends, so ownership cannot change
between the check and the commit; a competing acquire waits for the lock and
then increments the token. A stale owner's transaction finds a higher token
and rolls back, and none of its writes become visible. Fig.~\ref{fig:fencing}
shows the sequence as it occurred on the cloud test bed when an engine
process was frozen for 35\,s.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.95\linewidth]{figures/fig_4_3_lease_fencing.png}
  \caption[Lease expiry and fencing of a stale owner]{Lease expiry and fencing
    of a stale owner, with the values measured in the freeze trials.}
  \label{fig:fencing}
\end{figure}

The token check is also the reason a separate coordination service is not
needed. A lease obtained from ZooKeeper or etcd would still require a token
check where the data is written; with the lease in the same database, the
check and the write are one transaction.

\section{Low-Level Design}
\label{sec:lld}

\subsection{Data model}

Table~\ref{tab:schema} lists the six tables. Every table except

primary key or its main index, so that each node's queries touch only the
rows of the shards it owns.

The primary key of \cd{events} is a second line of defence: even if two
writers passed the fencing check, they could not both append the same
sequence number.

\subsection{The workflow task loop}

A workflow makes progress only when a workflow task for it is processed.
Such a task is created when the run starts and whenever something the run is
waiting for happens: an activity completes or fails, a timer fires or a signal
arrives. Fig.~\ref{fig:taskloop} shows how a worker processes one task.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.92\linewidth]{figures/fig_4_4_task_loop.png}
  \caption[The workflow task loop]{The workflow task loop. All writes of one
    decision commit in a single fenced transaction.}
  \label{fig:taskloop}
\end{figure}

The worker loads the run's history and executes the workflow function from
the beginning. Each call on the workflow context is numbered by its position
in program order, $k = 0, 1, 2, \ldots$. If the history holds a result for
call $k$, the call returns that result immediately. The first call with no
recorded result ends the replay: the worker collects the new commands the
workflow has issued (schedule an activity, start a timer, complete the run)
and commits them as one \emph{decision}. The commit performs, in order: the
fencing check; admission of the run for a start, using the \cd{executions}
primary key as the start-idempotency check; appending the new events;
inserting the new tasks, timers and intents; updating the execution status;
and deleting the processed task. Either all of these become visible or none
do.

Using the program-order index $k$ as the join key between code and history
is what makes replay exact. A workflow that issues the same calls in the same
order matches its history call by call. A workflow whose code has been
changed in a way that alters the order is detected on replay, because the
command at position $k$ no longer matches the recorded event type, and the
run is failed with a non-determinism error instead of continuing with a
corrupted history.

Workflow code is run on a cooperative scheduler. Each workflow coroutine runs
until it blocks on a future, and the scheduler then runs the next ready one,
so that a workflow that starts several activities in parallel is still
executed in a deterministic order. Time, random numbers and unique
identifiers are obtained from the context, which returns recorded values
during replay.

\subsection{Task queue, timers and signals}

Workers poll the \cd{tasks} table with
\cd{SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1}, restricted to the shards the
node owns and to rows whose visibility time has passed and whose lock has
expired. The selected row is locked by setting \cd{locked\_until} and a new
\cd{lock\_token}. \cd{SKIP LOCKED} lets many workers poll the same shard
without waiting on each other. A long-running activity extends its lock with
a heartbeat; if the worker dies, the lock expires after 30\,s and the task is
delivered again.

Timers are rows with a fire time. A timer loop on the owning node selects due
timers, appends a \cd{TimerFired} event and creates a workflow task, in one
fenced transaction. A signal is appended directly to the target run's history
as a \cd{SignalReceived} event together with a workflow task, so a signal sent
while the run's shard is moving between nodes is not lost.

\subsection{Retries and the crash-window analysis}
\label{sec:crashwindows}

When an activity fails, the workflow worker applies the activity's retry
policy: an initial interval of 1\,s, a backoff coefficient of 2, a maximum
interval of 60\,s and at most five attempts by default, with a list of error
types that are not retried. The retry is a new task with a later visibility
time; the arguments are those recorded when the activity was first
scheduled.

Table~\ref{tab:crashwindows} considers each point at which a crash can occur
during one activity. In three of the four windows recovery is safe without
help from the activity. In window C the external effect has happened but the
engine has no record of it, and the activity will be called again.

\begin{table}[htbp]
  \centering
  \caption{Crash windows for one activity execution}
  \label{tab:crashwindows}
  \small
  \begin{tabular}{@{}p{0.2in}p{1.75in}p{2.45in}p{0.6in}@{}}
    \toprule
    & \textbf{Crash point} & \textbf{Recovery} & \textbf{Safe} \\
    \midrule
    A & Activity scheduled, not yet polled & Another worker polls the task;
      the activity runs once & Yes \\
    B & Task polled, external call not made & The lock expires and the task is
      redelivered; the activity runs once & Yes \\
    C & External call succeeded, completion not recorded & The lock expires
      and the task is redelivered; the external call is made again & No \\
    D & Completion recorded, workflow task not yet processed & Replay resolves
      the activity from history; it is not run again & Yes \\
    \bottomrule
  \end{tabular}
\end{table}

Window C cannot be closed by the engine, because the external service and the
engine's database are separate systems with no common transaction. The engine
provides the means for the external service to close it: every activity
receives a deduplication key formed from the run identifier and the
program-order index $k$, which is the same on every attempt and every replay.
An activity that passes this key as the idempotency key of the external call
turns a repeated call into a no-op at the service. The engine's guarantee is
therefore at-least-once execution of activities and exactly-once recording of
their results.

\subsection{Saga compensation}

Compensations are managed by a small saga object created inside the workflow
(Listing~\ref{lst:workflow}). A compensation is added with
\cd{AddCompensation} only after its forward step has returned successfully, so
a step that failed or never ran has nothing to undo. When a later step fails,
\cd{Compensate} runs the registered compensations as activities in reverse
order of registration.

The stack of compensations is not written to the history. It is a pure
function of the history, because on replay the workflow follows the same path,
observes the same successes and registers the same compensations in the same
order. Recording it would add an event per step and would create a second
copy that could disagree with the first. Each compensation is scheduled and
completed through the history like any other activity, with its own retries
and deduplication key, so a crash in the middle of a rollback resumes at the
first compensation that has not completed.

\subsection{Semantic deduplication}

The source of reworded duplicates is narrower than it may appear. An engine
retry of a scheduled activity reuses the recorded arguments, so exact matching
is enough. Reworded duplicates arise when an agent re-plans: replay resolves
an earlier plan and its tool call from history, but a later planning step
whose result was not yet recorded runs again and may express the same intent
in different words.

The similarity check is itself non-deterministic, since it depends on an
embedding model and on a threshold. If it were evaluated in the activity
worker, it would be re-evaluated on replay and could give a different answer,
and the history would diverge. The engine therefore evaluates it once, on the
workflow path, and records the verdict as an event, in the same way as a
\cd{SideEffect}. Listing~\ref{lst:semdedup} gives the procedure.

\begin{lstlisting}[caption={Semantic deduplication of an activity at position
  $k$}, label={lst:semdedup}]
first execution:
  intent     := canonical(type, normalised and sorted arguments)
  candidates := completed semantic activities of the same type in this run
  v          := embed(intent)                      // 384 dimensions
  (j, s)     := argmax over candidates of cosine(v, v_j)
  verdict    := DUPLICATE if s >= tau_high (0.90)
                DISTINCT  if s <  tau_low  (0.85)
                ESCALATE  otherwise
  append SemanticDedupEvaluated{k, verdict, j, s, thresholds, model}
  DUPLICATE: return the recorded result of activity j; schedule nothing
  DISTINCT:  schedule the activity as usual
  ESCALATE:  wait for an approval signal, or execute (per configuration)
replay:
  read SemanticDedupEvaluated{k} and apply the recorded verdict
  (no embedding call, no similarity computation)
\end{lstlisting}

Three properties follow. Replay needs no embedding service, so recovery does
not depend on its availability. Every verdict is stored with its similarity,
thresholds, matched activity and model name, so a suppressed action can be
explained after the fact. The candidate set is restricted to completed
activities of the same type in the same run, which keeps the comparison small
and makes a false match across unrelated runs impossible. The intent
embeddings are stored in \cd{activity\_intents} with the \cd{pgvector} type.

\subsection{Node runtime}

At start-up a node applies the schema migrations, connects to PostgreSQL,
builds the ring from the configured list of cluster nodes and starts the
lease manager. For each shard it acquires, it starts workflow, activity and
timer loops for that shard; when it loses a shard it stops them at once. The
fencing check would reject their writes in any case, but stopping them avoids
polling load on a shard the node no longer owns. On a graceful shutdown the
node stops taking new tasks, waits for in-flight tasks within the shutdown
grace period and releases its leases, so that the next owner can take over
without waiting for expiry. The defaults are four workflow workers and eight
activity workers per node; Chapter~7 measures the effect of changing them.
