\chapter{Literature Survey}

This chapter reviews the work on which the engine is built. Six bodies of
literature are relevant: durable execution and stateful serverless systems;
the partitioning of work across machines; leases, coordination and fencing;
long-running transactions and sagas; the failure modes of agent systems built
on language models; and semantic similarity and caching. Each section closes
with the point taken from it into the design. The chapter ends with a
comparison of the closest systems and a statement of the gap.

\section{Durable Execution and Stateful Serverless Workflows}

The principle that a computation can be recovered by re-executing it against
a log of its own decisions is older than the term durable execution. Lamport
showed that a deterministic state machine fed the same ordered inputs reaches
the same state~\cite{lamport1978}, and the write-ahead log of classical
transaction processing applies the same reasoning to database
pages~\cite{grayreuter1992}. Log-centred systems such as Kafka later made an
ordered, durable log the main interface between services~\cite{kafka2011}.
Durable execution engines apply the idea at the level of application code: the
inputs to the state machine are the results of the workflow's external calls,
and the log is the workflow's event history.

Temporal, which grew out of Uber's Cadence, is the most widely used engine of
this kind~\cite{temporaldocs}. Workflow code is written in an ordinary
programming language under a determinism contract; each external call is
recorded as a pair of scheduled and completed events, and recovery replays the
code against the history. Temporal partitions histories into a fixed number of
shards, and a membership service assigns shards to history service hosts. The
architecture is proven at large scale, but a deployment comprises frontend,
history, matching and worker services over a database, with an optional search
cluster for visibility queries. Restate takes a similar programming model but
embeds its own log and storage in a single binary~\cite{restatedocs}.

Durable Functions brought the model to serverless platforms. Burckhardt
\emph{et al.}\ give a formal semantics for orchestrations, entities and
replay, and prove that replay is correct when the orchestration code is
deterministic~\cite{durablefunctions2021}. Netherite replaced the original
storage provider with partitioned, speculatively committed logs and reported
large gains in throughput and latency~\cite{netherite2022}. Ambrosia earlier
proposed \emph{virtual resiliency}, in which logging and deterministic replay
make a distributed application behave as if it never failed, at the cost of
requiring every component to be deterministic~\cite{ambrosia2020}.

Two research systems from the serverless community address the same problem
with a shared log. Beldi provides exactly-once semantics and transactions for
stateful serverless workflows by logging every read and write in a linked
data-access log kept in a key-value store~\cite{beldi2020}. Boki builds a
shared log into the function runtime and offers durable workflows, object
storage and message queues as libraries over it~\cite{boki2021}. Both achieve
strong guarantees, and both depend on a purpose-built logging layer.

DBOS argues the opposite direction: that the state of an operating system,
including the state of running programs, belongs in a database~\cite{dbos2022}.
Its durable workflows checkpoint each step into PostgreSQL, so that recovery
needs nothing other than the database. R3 extends the approach to record and
replay of database-backed applications, so that a past execution can be
reproduced and modified retroactively~\cite{r3vldb2023}. DBOS is the system
closest in spirit to this project. It does not, however, partition workflows
across nodes with explicit ownership; recovery is driven by the database and
the executor that originally ran the workflow.

\paragraph{Taken into the design.} The workflow and activity split, the
determinism contract and the recovery-by-replay model come from Temporal and
Durable Functions. The decision to use PostgreSQL as the only store follows
DBOS. The engine differs from all of them in combining a single-dependency
deployment with explicit, fenced shard ownership.

\section{Partitioning Work Across Machines}

A system that runs on more than one machine must decide which machine is
responsible for each piece of state. Consistent hashing, introduced by Karger
\emph{et al.}\ for web caches~\cite{consistenthash1997}, maps keys and
machines onto the same circle so that adding or removing a machine moves only
the keys adjacent to it. Dynamo applied the technique to a replicated
key-value store and introduced virtual nodes, several positions per physical
machine, to even out the load~\cite{dynamo2007}.

Hashing keys directly to machines has a drawback when the state behind each
key is large or when ownership must be transferred carefully: every
membership change touches many independent keys. Systems with expensive
ownership transfer therefore introduce a fixed intermediate layer. Slicer, at
Google, maps keys to slices and assigns slices to tasks, rebalancing the
assignment from observed load~\cite{slicer2016}. Shard Manager at Meta
generalises this into a platform that places and migrates shards for hundreds
of applications, and reports that a fixed shard count with movable assignment
is the dominant pattern in practice~\cite{shardmanager2021}. Borg schedules
the processes that host such shards~\cite{borg2015}.

\paragraph{Taken into the design.} The engine uses the two-level scheme of
Slicer and Shard Manager: a workflow hashes to one of a fixed number of shards
for its whole life, and shards are assigned to nodes by a consistent-hash ring
with virtual nodes. A change of membership moves ownership but no data,
because all data is in the shared database.

\section{Leases, Coordination and Fencing}

Assigning a shard to a node is only half of the problem; the system must also
ensure that a node that has lost a shard stops writing to it. Gray and
Cheriton introduced leases, time-bounded grants of authority that expire
unless renewed, so that a crashed holder cannot block others
forever~\cite{leases1989}. A lease is safe only under assumptions about clock
drift and process pauses. A holder that is paused, for example by garbage
collection or by a virtual machine being descheduled, may resume after its
lease has expired and act on authority it no longer has. Kleppmann describes
this failure and the standard remedy: a \emph{fencing token}, a number that
increases with every grant, which the storage layer checks on every
write~\cite{kleppmann2017}.

Production systems usually obtain leases from a coordination service. Chubby
provides coarse-grained locks with sequencers that serve as fencing
tokens~\cite{chubby2006}, and ZooKeeper provides the primitives from which
leader election and locks are built~\cite{zookeeper2010}. Both rest on a
consensus protocol such as Paxos or Raft~\cite{raft2014}. The impossibility
result of Fischer, Lynch and Paterson shows why some timing assumption is
unavoidable: in a purely asynchronous system no protocol can both tolerate a
crash and always terminate~\cite{flp1985}. Leases embody that assumption
explicitly.

\paragraph{Taken into the design.} A coordination service is not required if
the store that holds the protected data can itself perform a linearizable
compare-and-swap. PostgreSQL can, through row locks. The engine therefore
keeps one lease row per shard and makes every write transaction check the
fencing token under \cd{SELECT ... FOR UPDATE}~\cite{postgresdocs}. The token
check happens in the same transaction as the write, which is the property the
literature identifies as essential.

\section{Long-Running Transactions and Sagas}

Garcia-Molina and Salem defined a saga as a long-lived transaction written as
a sequence of shorter transactions, each paired with a compensating
transaction that semantically undoes it~\cite{sagas1987}. If the saga fails
part way, the compensations for the completed steps are run in reverse order.
Helland later argued that applications which span services cannot rely on
distributed transactions at all, and must be built from idempotent operations
on individually addressed entities~\cite{helland2007}. Recent work on
microservices has examined the isolation anomalies that sagas permit and
proposed remedies such as semantic locks and versioning~\cite{daraghmi2022}.

Two points from this literature matter here. A compensation is an action with
its own side effects and can itself fail, so it must be retried and
deduplicated in the same way as a forward step. The order and completeness of
compensation must also survive a crash in the middle of rolling back.

\paragraph{Taken into the design.} Compensations are ordinary activities,
registered as each forward step completes and run in reverse order. Because
they are activities, their scheduling and completion are recorded in the
event history, and a crash during rollback is recovered by replay like any
other.

\section{Failure Modes of Agent Systems}

Agents built on language models are a new class of long-running workflow. An
agent plans, calls tools that act on the world, observes the results and plans
again. Cemri \emph{et al.}\ analysed traces from several multi-agent
frameworks and organised the observed failures into a taxonomy; step
repetition and failure to recognise that a task was already complete appear
among the recurring categories~\cite{whyfail2025}. Microsoft's AI Red Team
reached a similar list from the security side, including repeated or
unintended actions after an interruption~\cite{msredteam2025}.

The relevance to durable execution is specific. A conventional engine records
the arguments of each step when it is scheduled, so an engine-level retry of
that step uses identical arguments. An agent that crashes between two planning
steps, however, will re-run the second planning step on recovery, and at a
non-zero sampling temperature it may describe the same action in different
words. The engine sees a new step with new arguments.

\section{Semantic Similarity and Caching}

Sentence-BERT made it practical to compare the meaning of two sentences by the
cosine similarity of fixed-size embeddings~\cite{sbert2019}, and MiniLM showed
that a small distilled model can produce such embeddings at a fraction of the
cost of the original~\cite{minilm2020}. Semantic caches for language-model
services build on this. GPTCache returns a stored answer when a new prompt is
close enough to a cached one~\cite{gptcache2023}; MeanCache adapts the
threshold to each user~\cite{meancache2025}; and vCache argues that a single
global threshold is unreliable and learns per-entry thresholds with an error
bound~\cite{vcache2025}.

A semantic cache and a semantic deduplication check fail in opposite
directions. A false hit in a cache returns a slightly wrong answer, which the
user can retry. A false match in a deduplication check suppresses an action
the user wanted, which is worse than missing a duplicate. The cache literature
therefore informs the mechanism but not the policy.

\paragraph{Taken into the design.} The engine uses a small sentence-embedding
model and a cosine threshold, but adopts a conservative policy: semantic
matching is opt-in per activity, candidates are restricted to completed
activities of the same type in the same run, an uncertain band between two
thresholds is escalated rather than decided, and every verdict is recorded in
the history.

\section{Research Gap}

The survey leaves three gaps. First, the engines that partition
workflows across machines do so with several cooperating services or a
coordination service, while the engine that needs only a database does not
partition. No system in the survey provides partitioned, fenced ownership
using only the database that already stores the workflow state. Second,
fencing is well understood in principle, but published descriptions rarely
report how often a stale owner actually attempts a write in a real deployment,
or how long ownership takes to move after a failure. Third, every engine
deduplicates steps by exact comparison of arguments, which fails for an agent that
re-plans after a crash, and the semantic
caching work that could detect such repeats is designed for a setting in which
a false match is cheap. This project addresses all three.
