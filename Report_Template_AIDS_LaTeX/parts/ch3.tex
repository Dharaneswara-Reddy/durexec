\chapter{Requirements and Analysis}

This chapter states what the engine must do and the conditions under which it
must do it. Functional requirements are numbered FR-1 to FR-12 and
non-functional requirements NFR-1 to NFR-8, so that later chapters can refer
to them. The chapter ends with the analysis that led to the chosen approach.

\section{Functional Requirements}

Table~\ref{tab:fr} lists the functional requirements. They follow from the
objectives in Table~\ref{tab:objectives}.

\begin{table}[htbp]
  \centering
  \caption{Functional requirements}
  \label{tab:fr}
  \small
  \begin{tabular}{@{}p{0.5in}p{5.0in}@{}}
    \toprule
    \textbf{ID} & \textbf{Requirement} \\
    \midrule
    FR-1 & A client can start a workflow of a registered type with an
      identifier and an input. Starting the same identifier twice returns the
      existing run rather than creating a second one. \\
    FR-2 & Every state change of a run is appended to its history as an
      immutable event with a gap-free sequence number. \\
    FR-3 & A run interrupted by a crash at any point resumes from its history
      and reaches the same result it would have reached without the crash. \\
    FR-4 & Activities are executed by workers through a durable task queue,
      with a configurable retry policy and per-task lock timeout. \\
    FR-5 & Each activity receives a deduplication key that is identical on
      every attempt and every replay. \\
    FR-6 & Workflows can wait on durable timers and on named signals sent by
      clients; both survive restarts. \\
    FR-7 & A workflow can register compensations; on failure they run in
      reverse order of registration, and rollback survives a crash. \\
    FR-8 & Workflows are partitioned into a fixed number of shards, each owned
      by at most one node at a time. \\
    FR-9 & When a node fails, its shards are claimed by surviving nodes and
      their runs continue without loss of progress. \\
    FR-10 & A write by a node that no longer owns the shard is rejected. \\
    FR-11 & An activity may opt in to semantic deduplication. A request whose
      meaning matches a completed activity of the same type in the same run
      returns that activity's recorded result instead of executing again. \\
    FR-12 & Clients can query the status and history of a run, and operators
      can read metrics for throughput, latency, ownership and errors. \\
    \bottomrule
  \end{tabular}
\end{table}

\section{Software and Hardware Requirements}

The engine is written in Go~1.25 and uses the \cd{pgx} driver for
PostgreSQL. PostgreSQL~16 with the \cd{pgvector} extension stores all state,
including the 384-dimensional intent embeddings used for semantic
deduplication. Embeddings are produced by an \cd{all-MiniLM-L6-v2} model
served over HTTP. Metrics are exported in Prometheus format. Development and
local testing used Docker Compose; the cloud evaluation used Amazon EKS with
Terraform for provisioning. Table~\ref{tab:hw} gives the hardware used in
each setting.

\section{Assumptions and Constraints}

The design rests on the following assumptions.

\begin{enumerate}[leftmargin=*, itemsep=2pt]
  \item PostgreSQL provides serializable row locks and durable commits. The
    engine does not defend against a database that loses committed data.
  \item Clocks on engine nodes may drift by a small amount relative to the
    lease period. Lease expiry is computed with the database clock, so drift
    between engine nodes does not affect safety; fencing protects against
    pauses longer than the lease.
  \item Workflow code is deterministic. The engine provides deterministic
    replacements for time, random numbers and unique identifiers, and detects
    some violations at replay time, but cannot prove determinism in general.
  \item External services that are called by activities accept an
    idempotency key, or their operations are naturally idempotent.
\end{enumerate}

Two constraints were fixed at the start. The engine must not introduce any
infrastructure dependency beyond PostgreSQL, and all cloud resources must fit
the free-tier and low-cost instance types available to the project, which
ruled out larger database hosts and multi-zone deployments.

\section{Analysis of the Chosen Approach}

Three decisions shape the rest of the design, and each was taken by comparing
alternatives against the requirements.

\paragraph{State: event history or checkpoints.} A checkpointing design stores
the current state of each run and overwrites it after each step. It is
simple, but it records what the state is and not how it was reached, so a
crash between a side effect and the checkpoint leaves no trace of the side
effect, and debugging requires extra logging. An event history records every
decision; the current state is a function of the history, and the history is
also the audit trail. The cost is replay time for long histories. Event
sourcing was chosen because FR-2, FR-3 and FR-11 all depend on the history
being the single source of truth.

\paragraph{Ownership: coordination service or database rows.} A
coordination service such as ZooKeeper or etcd provides leases and watches,
but violates NFR-3 and adds a second system whose view of ownership can
disagree with the database. More importantly, a lease held in one system does
not by itself prevent a stale write to another: the token must be checked
where the data is written. Keeping the lease and the fencing token in the
same database as the workflow state lets a single transaction check ownership
and write the data, which satisfies FR-10 directly.

\paragraph{Task delivery: message broker or database queue.} A broker would
offer higher raw throughput, but an activity's completion must be recorded in
the history atomically with the removal of its task; with a separate broker
this requires an outbox and a relay. A queue table polled with
\cd{SELECT ... FOR UPDATE SKIP LOCKED} gives atomic hand-off within one
transaction. The cost, measured in Chapter~7, is polling load on the database
when the cluster is idle and lock contention at high load.

The price of these decisions is that the database is both the availability
floor and the throughput ceiling of the system. The evaluation in Chapter~7
was designed to locate that ceiling and to show what happens beyond it.
