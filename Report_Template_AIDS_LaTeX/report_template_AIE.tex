% ---------------- ABSTRACT -------------------------------------------
\frontchapter{ABSTRACT}
\begin{spacing}{1.5}
Long-running business processes --- placing an order, settling a payment,
provisioning infrastructure, or driving a multi-step artificial-intelligence
agent --- span many services and may take seconds or days to finish. Because
their individual steps touch the outside world, a crash partway through leaves
a system that keeps no durable record of progress only two possible outcomes,
and both are incorrect: the completed work is lost, or it is repeated and a
customer is charged twice. Industry has converged on \emph{durable execution
engines} to eliminate this class of failure, but the mechanisms that make one
work --- event sourcing, deterministic replay, partitioned ownership and
fenced failover --- are seldom implemented from first principles in an
academic setting, and existing engines each require between four and six
cooperating infrastructure components. This report presents the design and
implementation of \emph{durexec}, an original durable execution engine written
in Go whose only infrastructure dependency is PostgreSQL. Every decision a
workflow makes is appended to an immutable event log before it is acted upon;
recovery is performed by re-executing the workflow function against that log,
so a process resumes on a different machine at precisely the point the failed
one reached. Execution is partitioned across a fixed set of shards by
consistent hashing, and ownership of each shard is held as a renewable lease
in a database row guarded by a monotonic fencing token that every mutating
transaction re-verifies --- providing the safety property normally obtained
from ZooKeeper or Raft without operating a second cluster. The engine further
contributes a \emph{semantic idempotency} mechanism that compares the meaning,
rather than the bytes, of an action an agent is about to perform against the
actions already recorded in the workflow's own history, in order to suppress
the re-worded duplicate side effects that exact-match deduplication provably
cannot detect. The verdict is computed once and journalled as an event, which
keeps replay deterministic, offline and auditable. This report covers the
problem formulation, a survey of the 2020--2026 literature, the requirements
analysis, and the complete high-level and low-level design of the engine.
\end{spacing}
