\frontchapter{ABSTRACT}
\begin{spacing}{1.5}
A long-running workflow, such as an order, a payment or a multi-step software
agent, changes the state of several external services, and a crash part way
through it either loses paid-for work or repeats work that must not happen
twice. Durable execution engines prevent this by journalling every workflow
decision and recovering by deterministic replay, but production engines depend
on four to six infrastructure services. This report presents \emph{durexec}, a
durable execution engine in Go whose only dependency is PostgreSQL. Workflows
are hashed to a fixed set of shards; each shard is owned through a lease held
in a database row, and a fencing token re-checked inside every write
transaction stops a node that has lost its lease from committing. A journalled
semantic check lets the engine recognise a reworded retry of an action already
taken by a language-model agent. On Amazon EKS with three engine nodes and one
PostgreSQL host, a closed-loop workload reached 131 workflows per second at a
99th-percentile latency of 3.1~s, limited by database CPU, and the sustainable
open-loop rate was about 100 workflows per second. Workers, shards and engine
replicas changed throughput by at most 19\%, and extra replicas gave no gain
while the database was the bottleneck. In sixteen fault-injection trials,
covering engine termination, a 35~s process freeze, loss of database
connections, a node drain and a database reboot, every accepted workflow
completed, no journal invariant was violated and every write by a stale owner
was rejected.

\vspace{4pt}
\textbf{Keywords:} durable execution, event sourcing, deterministic replay,
leases, fencing tokens, sharding, fault tolerance, PostgreSQL.
\end{spacing}
